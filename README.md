# OPcache Guard

Инвалидирует OPcache для файлов, заменённых обновлением плагина, темы или ядра.
Нужен сайтам с `opcache.validate_timestamps=0`: PHP никогда не проверяет
изменения файлов, поэтому после обновления часть воркеров продолжает исполнять
старый байткод — сайт отвечает 502 или фаталом до перезапуска PHP-FPM.

Версия 1.3.1. Требуется WordPress 7.0+, PHP 8.0+.

## Что покрыто

| Случай | Действие |
|---|---|
| Установка плагина (`action=install`) | обход каталога и `opcache_invalidate( $file, true )` для каждого `*.php` |
| Обновление плагина | то же для каталога обновлённого плагина |
| Обновление темы | то же для каталога темы |
| Обновление ядра | один `opcache_reset()`: обход `ABSPATH` дороже перекомпиляции пула |
| Удаление плагина (`deleted_plugin`) | инвалидация пути удалённого файла (force работает и для несуществующих файлов) и каталога |
| Переключение темы (`switch_theme`) | каталоги нового и прежнего шаблона |
| Активация / деактивация плагина | каталог этого плагина, без полного сброса |
| Сохранение в редакторе плагинов, редакторе темы, AJAX-редакторе | сохранённый файл + отложенная задача на его каталог |
| Правка файлов мимо WordPress (FTP, rsync) | хука нет: `wp opcache-guard flush` или `wp opcache-guard arm` |
| Цель больше 5 000 файлов или обход дольше 5 секунд | один `opcache_reset()` вместо обхода |

Инвалидация **по файлам**, а не полным сбросом: пул OPcache может быть общим для
нескольких сайтов, и `opcache_reset()` заставит перекомпилировать всё у всех.

## Отложенный проход: зачем он нужен

`opcache_reset()` и `opcache_invalidate()` действуют **только в том пуле
PHP-FPM, который обслужил запрос**. Если админка и сайт работают в разных пулах,
сброс из `wp-admin` очищает пул админки, а фронтенд продолжает отдавать старый
байткод. Это же объясняет, почему «сброс кэша» из одного пула не помогает на
такой конфигурации.

Поэтому после обновления плагин:

1. сразу инвалидирует файлы в текущем пуле;
2. ставит короткоживущую опцию `opcache_guard_pending` со списком затронутых
   каталогов и временем истечения (15 минут);
3. на `init` (приоритет 99) в **любом** следующем обычном запросе выполняет ту же
   пофайловую инвалидацию для этих каталогов.

Опция не удаляется после первого прохода: каждый пул должен получить свой.
Между проходами выдерживается пауза 60 секунд, а параллельные воркеры одного пула
разводит короткий лок `opcache_guard_lock` (атомарный `add_option()`); запрос,
проигравший гонку, оставляет задачу следующему. Через 15 минут опция удаляется.
Отложенный проход никогда не делает полный сброс — только пофайловую
инвалидацию с тем же лимитом. Вторым шагом он сбрасывает соседние пулы через
FastCGI, если сокет настроен.

## Немедленный сброс через FastCGI

Плагин содержит минимальный FastCGI-клиент: он подключается к сокету FPM и
просит **сам себя** выполнить сброс. Запрос идёт на файл плагина с серверным
параметром `OPCACHE_GUARD_RESET_INTERNAL=1`; такой параметр может прийти только
по FastCGI — из HTTP он пришёл бы как `HTTP_OPCACHE_GUARD_RESET_INTERNAL`, и
обработчик в начале файла его не увидит. Ответ — `OK` или `FAILED`, WordPress в
этом запросе не загружается.

Сокет задаётся одним из двух способов:

```php
// wp-config.php
define( 'OPCACHE_GUARD_FASTCGI', '/run/php/php8.4-fpm.sock' ); // или 127.0.0.1:9000
```

или берётся `address:` из `.cachetool.yml` рядом с WordPress. Без настройки шаг
тихо пропускается.

FastCGI-сброс используется в `wp opcache-guard flush` и вторым шагом отложенного
прохода: так соседние пулы очищаются сразу, не дожидаясь следующего запроса.

## opcache.file_cache

Если включён `opcache.file_cache`, скомпилированные скрипты лежат ещё и в этом
каталоге, поэтому одного `opcache_reset()` мало: при полном сбросе (ядро,
превышение потолка), в `wp opcache-guard reset` и в отложенном проходе при
`opcache.file_cache_only=1` плагин **поворачивает** каталог — переименовывает в
`<dir>.rm-<uniqid>`, удаляет и создаёт пустой. Если переименование невозможно
(точка монтирования, другая ФС), каталог удаляется на месте. Путь, который не
является каталогом, не трогается; ошибки глушатся.

## WP-CLI

```bash
wp opcache-guard status [--format=table|json]   # enabled, cached scripts, hits, misses,
                                                # память, hit rate, file_cache,
                                                # validate_timestamps, sapi,
                                                # deferred.pending/last, fastcgi socket
wp opcache-guard reset [--force]                # полный сброс в текущем пуле + file_cache
                                                # + FastCGI-сброс соседних пулов
wp opcache-guard flush                          # пофайловая инвалидация плагинов и тем
                                                # + FastCGI + отложенная задача
wp opcache-guard arm [--minutes=15]             # только поставить отложенную задачу
```

`flush` полезен после заливки файлов по FTP, когда хуки WordPress не срабатывают.
`arm` нужен, когда перезапустить PHP-FPM нельзя и сокета нет: поставьте задачу и
откройте сайт один раз — каждый пул очистит свой кэш на первом обычном запросе.
`--force` у `reset` сбрасывает даже если OPcache выглядит выключенным.

**Страницы статуса в админке нет и не планируется**: состояние смотрят через
`wp opcache-guard status`.

## Уведомления в админке

После сохранения файла в редакторе плагинов, редакторе темы или AJAX-редакторе
на следующей странице админки показывается dismissible-уведомление: «Файл
сохранён, кэш OPcache инвалидирован». Если инвалидация не удалась, в уведомлении
указана причина (`opcache.restrict_api`, `opcache.file_cache_only`, выключенный
OPcache). Это UI, а не лог.

## Правка файлов из админки и активация

- **Редакторы.** На `load-plugin-editor.php` / `load-theme-editor.php` (и на
  AJAX-хуке `wp_ajax_edit-theme-plugin-file` до обработчика ядра) запоминается
  путь файла и хеш его содержимого. Ядро проверяет nonce и записывает файл, после
  чего в фазе `shutdown` плагин инвалидирует сохранённый файл и ставит
  отложенную задачу на каталог. При неверном nonce ядро делает `wp_die` до
  записи, хеш не меняется — инвалидации нет.
- **AJAX-редактор** определяется по полям `file` + `plugin`/`theme`, которые ядро
  само проверяет в `wp_edit_theme_plugin_file()`; путь нормализуется
  (`realpath()`) и проверяется, что он лежит внутри каталога плагина или темы.
- **Активация и деактивация.** Файлы не меняются, но плагин, залитый по FTP до
  активации, может быть закэширован со старым содержимым. Каталог инвалидируется
  пофайлово, без полного сброса, плюс отложенная задача.

## Немедленный сигнал во фронтенд-пул (loopback)

Отложенный проход ждёт следующего запроса посетителя. Чтобы не ждать, сразу
после обновления плагин отправляет **один неблокирующий запрос на главную
страницу сайта** (`home_url( '/' )`) с одноразовым токеном:

```text
https://example.org/?opcache_guard_ping=<hash>
```

- `home_url()`, а не `admin_url()`: задача — попасть в пул, который отдаёт
  страницы. Запрос идёт с `blocking => false`, `timeout => 0.01` и заголовком
  `Cache-Control: no-cache`.
- Токен — `wp_hash()` от списка каталогов и срока задания, живёт не дольше
  **5 минут** и хранится в том же ожидающем задании.
- На `init` запрос с `opcache_guard_ping` проверяется через `hash_equals()` и
  срок; при совпадении пул **сразу** инвалидирует каталоги, не дожидаясь
  60-секундной паузы, и удаляет токен. Ответ не меняется: ничего не
  печатается, код ответа прежний, в лог ничего не пишется.
- Токен одноразовый: повторный запрос с тем же значением ничего не делает, а
  просроченный просто игнорируется.

Отключить отправку можно фильтром — например, если firewall, Basic-авторизация
или прокси не пускают сайт к самому себе:

```php
add_filter( 'opcache_guard_loopback', '__return_false' );
```

Тогда остаётся прежний отложенный проход: первый обычный запрос каждого пула
почистит свой кэш. Loopback не отправляется из посторонних AJAX-, cron- и
REST-запросов, но **сам запрос обновления** его отправляет, даже когда это
`admin-ajax.php` — кнопка «Обновить» на экране «Плагины» работает именно так.
Из запроса, который сам пришёл с токеном, loopback не отправляется никогда. Если отправка не удалась, отложенное
задание уже сохранено и продолжит работать. Страничный кэш может отдать ответ на
ping из кэша — тогда сработает тот же отложенный проход.

## Массовые обновления

При обновлении нескольких плагинов за раз `upgrader_process_complete` срабатывает
на каждый плагин, но loopback из них **один**: цели складываются в одно
pending-задание, а запрос отправляет ровно один ping в фазе `shutdown`, когда
WordPress уже закончил запись. Шестнадцать обновлений в одном запросе — один
ping, а не шестнадцать.

Во время режима обслуживания loopback **не отправляется**: если существует
`ABSPATH/.maintenance`, ping остаётся в задании и сработает позже, когда
обслуживание закончится (обычный `init`-проход). То же при уже прерванном
соединении (`connection_aborted()`).

Отдельно стоит знать: массовое обновление «всех сразу» может уронить сам
WordPress. `wp_maintenance()` сначала проверяет `file_exists( ABSPATH .
'.maintenance' )`, а затем `require` того же файла; при массовом обновлении файл
создаётся и удаляется несколько раз, и запрос, попавший в промежуток между
проверкой и `require`, получает фатал. `WP_Fatal_Error_Handler` тоже вызывает
`wp_is_maintenance_mode()`, поэтому обработчик фаталов падает вместе с ним. Это
гонка в ядре WordPress, а не в плагине: обновляйте плагины небольшими партиями.

## Ограничения (важно)

- **Сброс из одного пула не достигает другого.** `opcache_reset()` в
  `wp-admin` не чистит пул фронтенда, а сброс из CLI не чистит ни один FPM-пул.
  Для этого существуют отложенный проход и FastCGI-сброс.
- **CLI-кэш не сбрасывается никогда.** У CLI отдельный OPcache (если
  `opcache.enable_cli=1`), и ни сброс из FPM, ни `wp opcache-guard flush` до
  пулов сайта не достают.
- **Общий пул между сайтами.** Если OPcache зашарен, полный сброс задевает все
  сайты на сервере, поэтому по умолчанию инвалидация идёт по файлам.
- **Ручная заливка файлов** (FTP, rsync, распаковка вручную) не вызывает хуков
  WordPress: используйте `wp opcache-guard flush` (с настроенным сокетом он
  сбросит и FPM-пулы) или `wp opcache-guard arm` и один запрос к сайту.
- **Обновление ядра** в отложенном проходе чистит `wp-admin` и `wp-includes` по
  файлам; остальное надёжнее добить перезапуском PHP-FPM.
- **`opcache.restrict_api`** может запрещать вызовы из файлов плагина. Тогда
  инвалидация не выполняется, а уведомление и `wp opcache-guard status`
  показывают причину.
- **Альтернатива без плагина:** `opcache.validate_timestamps=1` и
  `opcache.revalidate_freq` (например, 2 секунды или 0 для немедленной проверки).
  Это медленнее на каждом запросе, зато не требует ни этого плагина, ни
  перезапуска FPM.
- **Прочие пулы:** если у сайта несколько пулов (админка, фронтенд, cron),
  каждый чистится своим первым запросом в течение 15 минут после обновления или
  сразу — через FastCGI, если задан сокет.

## Логи

Плагин **ничего не пишет в лог**: ни `error_log`, ни свои файлы. Результат
работы виден в уведомлениях админки и в `wp opcache-guard status`.

## Константы и фильтры

Пороги можно переопределить в `wp-config.php` до загрузки плагина:

| Константа | По умолчанию | Смысл |
|---|---|---|
| `OPCACHE_GUARD_FASTCGI` | не задана | сокет FPM для немедленного сброса соседних пулов |
| `OPCACHE_GUARD_MAX_FILES` | `5000` | цель с бо́льшим числом файлов инвалидируется полным сбросом |
| `OPCACHE_GUARD_MAX_SECONDS` | `5.0` | цель, обход которой дольше, тоже инвалидируется полным сбросом |
| `OPCACHE_GUARD_DEFERRED_TTL` | `900` | сколько живёт отложенная задача |
| `OPCACHE_GUARD_DEFERRED_INTERVAL` | `60` | пауза между отложенными проходами |
| `OPCACHE_GUARD_LOCK_TTL` | `60` | брошенный лок снимается через столько секунд |

Для тестов и нестандартных серверов есть фильтры: `opcache_guard_enabled`
(принудительно включить/выключить проверку), `opcache_guard_max_files`,
`opcache_guard_max_seconds`, `opcache_guard_deferred_ttl`,
`opcache_guard_deferred_interval`.

## Обновления

Плагин обновляется штатным механизмом WordPress из репозитория
[Gnoztis/opcache-guard](https://github.com/Gnoztis/opcache-guard): берётся
последний релиз, а если релиза нет — тег вида `X.Y.Z` (префикс `v` тоже
принимается). Проверка кэшируется на 6 часов, неудачная повторяется через
15 минут; кнопка «Проверить обновления» в строке плагина сбрасывает кэш.

Анонимный лимит GitHub API — 60 запросов в час на IP. Если на сервере несколько
сайтов, задайте в `wp-config.php` свой токен (fine-grained, право
**Contents: Read**), это поднимает лимит до 5000:

```php
define( 'OPCACHE_GUARD_GITHUB_TOKEN', 'github_pat_...' );
```

## Данные в базе

Опции `opcache_guard_state` (одноразовые флаги), `opcache_guard_pending`
(отложенная задача), `opcache_guard_lock` (лок), транзиент
`opcache_guard_editor_notice` (уведомление редактора) и транзиенты апдейтера
`opcache_guard_github_release*`. `uninstall.php` удаляет всё перечисленное.
